- 增加支持初始状态的跨分块无损扫描 `forward_chunked()`，峰值激活受 `chunk_size` 限制。
- 增加 FP32/BF16 状态快照序列化与 SHA-256 完整性校验。
- 让 `generate()` 使用分块状态预填充，降低长 prompt 的中间激活峰值。

## 2. 核心代码与文件改动

- `tricore/model.py`：
  - `TriCoreBlock.forward_with_state(x, state=None, step_offset=..., ...)`：分块局部扫描；当 state 非空时，局部 `t=0` 也必须执行 Delta/Hebbian 写入与 reset 检查。
  - `TriCoreLM.forward_chunked(idx, chunk_size=256, states=None, return_states=False)`：在完整 `idx` 上计算 masks，再按 `chunk_size` 切片；逐层携带 `(h, F_mat, prev_k)`。
  - `save_state_snapshot(states, path=None, compress_bf16=False)`：写入架构、dtype、字节账本、SHA-256 与张量。
  - `load_state_snapshot(snapshot_or_path, device="cpu", dtype=torch.float32)`：校验格式/架构/层数/形状/SHA-256 后恢复状态。
  - `generate()`：prompt 预填充改为 `forward_chunked(..., chunk_size=256, return_states=True)`。
- `tricore/cli.py`、`tricore/__main__.py`：`info`、`verify`、`benchmark` 三子命令。
- `tricore/__init__.py`：`__version__ = "1.6.4"`。
- `pyproject.toml`：版本 `1.6.4`，`[project.scripts] bedrock-tricore = "tricore.cli:main"`。
- `tests/test_v7_streaming.py`：新增 `test_v164_chunked_prefill_equivalence` 与 `test_v164_state_snapshot_and_cli`。
- `docs/versions/`：本文件、v1.6.0–v1.6.3 复盘、历史 V4–V13 切片与 INDEX。

## 3. 真实问题与根因排查

### 3.1 分块边界 t=0 不能简单跳过写入

原 `tricore_fused_scan` 在序列起点 `t=0` 不写入，因为没有前置 `prev_k`。但第二个分块的局部 `t=0` 对应全局 `t>0`，此时已经持有上一分块末尾的 `prev_k`；若仍按“局部 t=0 不写”处理，会丢掉边界处的 Delta/Hebbian 更新，导致分块输出与逐 Token 结果不一致。

### 3.2 语法掩码不能按分块重新发现

`_build_masks` 使用整条序列的 token 频率与末尾 delimiter；若对每个 chunk 单独计算，频率统计和 delimiter 位置会改变，autonomous syntax 掩码会漂移。正确做法是先在完整 `idx` 上算 masks，再按 chunk 切片。

### 3.3 BF16 快照的 SHA-256 与 dtype 转换

直接对 BF16 张量做 NumPy 转换不稳定；若先转 FP32 再哈希，又必须保证保存与加载使用同一规则，否则校验和会误报。根因是“存储 dtype”和“哈希规范化 dtype”没有分离。

### 3.4 构建隔离环境仍可能访问不可用镜像

`python -m build` 的隔离环境重新安装构建依赖；本机 pip index 指向清华镜像时可能返回 403。根因与项目代码无关，是构建环境沿用了用户级 index 配置。

## 4. 解决方案

- `forward_with_state` 以 `state is not None` / `step_offset > 0` 区分“真正序列起点”和“跨分块延续点”；延续点局部 t=0 正常写入，并在 `prev_k_new` 后应用 `reset_mask`。
- `forward_chunked` 在完整序列上计算 `separator_mask`、`reset_mask` 与 `role_logits`，再按 chunk 切片；逐层把状态传给下一个 chunk。
- 快照统一在 CPU 上保存；BF16 压缩只改变存储 dtype，SHA-256 对 BF16 先规范化为 FP32 再计算，加载时使用同一规则，并在恢复前校验架构/层数/形状/哈希。
- 构建使用 `python -m build --no-isolation`，并在发布前执行 `twine check` 与 wheel/sdist 元数据检查。
- CLI `verify` 固化为：17,408 B 不变量、`forward_chunked` vs `forward_step`、FP32/BF16 快照、SHA-256、热恢复继续推理。
